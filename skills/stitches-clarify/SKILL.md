# Stitches Clarify

这个 Skill 是 Stitches `clarify` 阶段的分析编排器。目标是把模糊需求整理成
可以进入设计阶段的 `proposal.md`。

## 先澄清，再分析

只有 `change-id` 不算需求输入。需求信息不足时，必须先向用户提出 3 到 5
个有针对性的问题，并等待用户回答；在收到回答前，不得创建或填写
`proposal.md`，也不得调用后续分析工具来替用户猜测需求。

问题至少覆盖：

- 想解决什么问题，目标用户是谁
- 期望出现什么行为
- 哪些内容在范围内，哪些内容不在范围内
- 如何判断完成
- 是否有约束、兼容性要求或已知方案

收到回答后，先用一段简短摘要复述需求，并请用户确认。用户确认后，才进入
CodeGraph、Context7、头脑风暴和 DeepReview。

## 核心流程

按以下顺序执行：

```text
用户澄清 -> CodeGraph -> Context7 -> 头脑风暴 -> 用户确认方案 -> DeepReview -> proposal.md
```

### 1. CodeGraph：代码影响

CodeGraph 不负责向用户提问，而是建立当前项目的代码上下文。对于代码行为
变更，优先使用 CodeGraph 或当前可用的代码关系分析工具，检查：

- 相关模块、符号和调用方
- 数据流和控制流
- 受影响的文件
- 现有测试和覆盖边界
- 可能的影响范围

如果 CodeGraph 不可用，使用项目已有的搜索、LSP、测试和构建工具替代，并在
提案中记录降级原因。不得声称已经调用不可用的工具。

### 2. Context7：外部知识

当需求涉及框架、库、API、协议、配置格式或版本行为时，查询 Context7 或
当前可用的官方文档 MCP。记录：

- 使用的库和版本
- 相关 API 或约束
- 官方文档中的关键结论
- 文档链接或查询依据

如果需求完全是项目内部逻辑，可以跳过，并在提案中说明“无外部文档依赖”。

### 3. 头脑风暴：方案比较

除极小的文字或配置修改外，至少提出两个候选方案。每个方案说明：

- 核心做法
- 受影响的文件或模块
- 实现成本
- 主要风险
- 适用条件

明确推荐方案和不推荐其他方案的原因。Bugfix 至少比较“最小修复”和“结构性
修复”是否值得采用。

头脑风暴完成后，向用户展示候选方案、推荐方案和主要取舍，并等待用户确认
采用哪个方案。没有方案确认前，不得进入 DeepReview 或写入最终提案。

### 4. DeepReview：反向审查

使用 DeepReview Skill、MCP 或同等的独立审查步骤，重点挑战前面的结论：

- 是否遗漏了用户目标或边界条件
- 是否存在未经验证的假设
- 是否会破坏兼容性、权限、安全或性能
- 是否遗漏测试、迁移或回滚方案
- 是否有更简单且风险更低的方案

如果没有可用的 DeepReview 工具，进行同样的人工反向审查，并记录降级原因。

## 输出要求

只有用户确认澄清摘要和推荐方案后，才将整理后的结论写入：

```text
openspec/changes/<change-id>/proposal.md
```

提案至少包含：

```md
## 上下文
## 代码影响分析
## 头脑风暴方案
## 深度审查
## 为什么做
## 改变什么
## 影响范围
## 验收标准
## 未决问题
```

规划文档使用简体中文。不要在 clarify 阶段修改生产代码、测试代码、设计文档
或任务清单。完成后由 Stitches 命令执行：

```bash
stitches validate --after clarify --change <change-id>
stitches advance clarify --change <change-id>
```
