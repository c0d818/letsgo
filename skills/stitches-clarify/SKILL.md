# Stitches Clarify

这个 Skill 是 Stitches `clarify` 阶段的分析编排器。目标是把模糊需求整理成
可以进入设计阶段的 `proposal.md`。

## 先澄清，再分析

只有 `change-id` 不算需求输入。需求信息不足时，**一次只问一个问题**，每个
问题给出 2 到 4 个可选项（编号 1、2、3…）加一个“其他/自定义”，等用户回答
后再问下一个。不要一次抛出一堆问题。

提问规则：

- 能直接从项目或上下文推断的不要问；由模型自行判断信息是否足够——不够就
  继续一次一题地问，够了就停止并进入摘要确认。
- 每个问题必须给出编号选项，并在最合适的选项后标注（推荐）；选项尽量覆盖
  常见答案，末尾保留“其他（请说明）”。例如：

  ```text
  提醒方式用哪种？（直接回复编号即可）
  1. macOS 系统通知（推荐）
  2. 终端输出
  3. 邮件
  4. 其他（请说明）
  ```

- 明确告诉用户“直接回复编号即可选择”；用户回复数字或文字都按真实意图理解。
- 收到回答后，如果有下一个问题，继续一次一题；全部问完后，用简短摘要复述
  需求并请用户确认。用户确认前不得创建或填写 `proposal.md`。

问题至少覆盖：

- 想解决什么问题，目标用户是谁
- 期望出现什么行为
- 哪些内容在范围内，哪些不在范围内
- 如何判断完成
- 是否有约束、兼容性要求或已知方案

## 核心流程

按以下顺序执行：

```text
用户澄清 -> 代码影响分析 -> 外部知识 -> 头脑风暴 -> 用户确认方案 -> 反向审查 -> proposal.md
```

分析阶段只做一次，避免重复读取文件或重复调用工具。先收集，再一次性整理。

### 1. 代码影响分析

对于代码行为变更，使用项目已有的搜索、LSP、测试和构建工具检查：

- 相关模块、符号和调用方
- 数据流和控制流
- 受影响的文件
- 现有测试和覆盖边界
- 可能的影响范围

工具不可用时记录降级原因。不得声称已经调用不可用的工具。

### 2. 外部知识

当需求涉及框架、库、API、协议、配置格式或版本行为时，查询 Context7 或当前
可用的官方文档 MCP。记录：

- 使用的库和版本
- 相关 API 或约束
- 官方文档中的关键结论

如果需求完全是项目内部逻辑，可以跳过，并在提案中说明“无外部文档依赖”。

### 3. 头脑风暴：方案比较

除极小的文字或配置修改外，至少提出 **3 个候选方案**（不足 3 个时说明为什么），
每个方案说明：

- 核心做法
- 受影响的文件或模块
- 实现成本
- 主要风险
- 适用条件

用对比表呈现候选方案，并明确：

- 推荐哪个方案，为什么
- 其他方案为什么不推荐
- 有没有“考虑过但放弃”的方案及放弃原因

Bugfix 至少比较“最小修复”和“结构性修复”是否值得采用。头脑风暴完成后，向
用户展示候选方案、推荐方案和主要取舍，并等待用户确认采用哪个方案。没有方案
确认前，不得继续。

### 4. 反向审查（DeepReview）

草稿 `proposal.md` 写好后，派发 `@stitches-reviewer` 做一次只读反向审查，
重点挑战前面的结论：

- 是否遗漏了用户目标或边界条件
- 是否存在未经验证的假设
- 是否会破坏兼容性、权限、安全或性能
- 是否遗漏测试、迁移或回滚方案
- 是否有更简单且风险更低的方案

审查不通过时，根据问题修改草稿后重新派发审查；通过后才定稿。

## 输出要求

只有用户确认澄清摘要、确认推荐方案、且反向审查通过后，才将整理后的结论写入：

```text
openspec/changes/<change-id>/proposal.md
```

提案至少包含：

```md
## 上下文
## 代码影响分析
## 头脑风暴方案
## 反向审查
## 为什么做
## 改变什么
## 影响范围
## 验收标准
## 未决问题
```

规划文档使用简体中文。不要在 clarify 阶段修改生产代码、测试代码、设计文档
或任务清单。完成后由 Stitches 命令执行：

```bash
stitches validate --after clarify --change <change-id>
stitches advance clarify --change <change-id>
```
