# 设计决策与理由

本文记录 LetsGo 当前关键规则背后的理由、实测依据、代价和调整条件。规则不是为了
增加流程，而是为了避免已经在真实项目中发生过的失控行为。后续改变规则时，应同时
更新本文、自动测试和对应 Hook/模板，不能只改提示词。

## 决策摘要

| 编号 | 决策 | 核心理由 | 调整条件 |
| --- | --- | --- | --- |
| D-01 | 固定六阶段生命周期 | 让需求、设计、实现和验证证据可追溯，避免直接改代码后补文档 | 小型纯维护任务持续证明完整阶段成本过高 |
| D-02 | CodeGraph 默认一次、最多两次 | 第一次覆盖结构和调用链，第二次只补关键缺口；实测第三次收益低但重复消耗上下文 | 大项目数据证明两次不足，可改为“2 次＋明确批准” |
| D-03 | 不设置常驻监督 Subagent | 监督 Agent 会重复读取上下文、增加 token，且仍需另一个机制监督它 | Hook 无法表达的复杂质量判断成为主要失败来源 |
| D-04 | Reviewer 最多初审加一次复审 | 防止同一产物反复审查；两轮足以形成“发现问题→修订→确认”的闭环 | 统计显示第二轮经常仍因新问题而非未修问题阻塞 |
| D-05 | Agent 必须使用 `lg:` 命名空间 | 避免项目本地 Agent 与插件 Agent 同名时启动错误实现，也方便统一统计 | Claude Code 提供稳定的插件身份字段，可替代名称判断 |
| D-06 | Prompt 启动前校验结果协议 | 仅在 Agent 文档里写协议不可靠；实测主 Agent 曾注入旧协议并引发重复派发 | 平台提供原生结构化 Agent 返回值后可移除文本协议 |
| D-07 | Apply 固定 RED → GREEN → REFACTOR | 防止实现完成后补写“看似 TDD”的证据；失败测试提供缺陷确实存在的证据 | 纯文档、模板、注释或不改变生产行为的任务可记录豁免 |
| D-08 | Verify 必须“未验证验收项：0” | 测试通过不等于用户行为已验收；实测浏览器待办仍被错误归档，且真实运行发现白屏 | 无例外；不能执行的验收项应保持阻塞或修改验收标准 |
| D-09 | 当前状态和运行摘要各只保留一个 JSON | 保留恢复与审计能力，同时避免每个任务产生大量事件 JSON | 出现合规审计需求时，可另加可选的外部事件存储 |
| D-10 | 澄清问题与权限批准分开统计 | `AskUserQuestion` 是产品交互，不是手动批准；混算会误判自动化成本 | 平台直接提供标准化人工干预分类后可映射到平台指标 |
| D-11 | 生命周期完成后默认本地提交，不自动推送 | 本地提交可恢复、可审查，是正常交付；push 会改变远端，仍需明确授权 | 用户明确要求不提交，或无法安全区分既有工作区改动 |
| D-12 | 优先原生只读工具，不扩大 Node/Bash 白名单 | 减少无意义批准，同时不把任意脚本执行伪装成安全命令 | 新增可精确解析、目标路径明确的安全命令类别 |
| D-13 | 中文说明＋英文机器协议 | 中文提高协作可读性；ASCII 字段和固定状态值提高跨 Agent 解析稳定性 | 平台原生结构化返回取代文本协议 |
| D-14 | 中断后从状态文件恢复，不依赖对话记忆 | 上下文压缩或会话中断会丢失对话细节，文件状态更稳定、可验证 | 平台提供等价且可查询的持久任务状态 |
| D-15 | 硬门禁只用于可机械判断的不变量 | 顺序、次数、字段和验收计数适合 Hook；架构质量仍由 Agent/reviewer 判断 | 能可靠自动化的新不变量应先有失败案例和测试再加入 |

## D-01：固定生命周期，而不是随机进入实现

LetsGo 使用 `clarify -> design -> plan -> apply -> verify -> archive -> done`。每一阶段
解决不同问题：clarify 确认目标，design 选择方案，plan 把工作拆小，apply 产生代码与
TDD 证据，verify 对照验收标准，archive 沉淀长期规格。状态机禁止跳阶段，是为了让
中断恢复和 reviewer 审查都有明确基准，而不是依赖主 Agent 的对话记忆。

代价是小任务也有流程成本。因此 maintenance、纯文档和仅测试任务允许在 apply 中记录
非行为豁免，但不允许伪造 RED。

## D-02：CodeGraph 为什么最多两次

第一次查询应一次返回目标源码、调用路径和影响范围。只有第一次缺少会改变设计结论的
关键调用边时，才允许第二次聚焦补查；零结果则立即降级到 Read/Grep。真实
`rain-agent` 试运行调用了三次，但第三次没有带来相称的新信息，反而增加上下文、耗时
和 token，所以 0.4.1 把文字建议升级为 Hook 硬门禁。

两次不是技术极限，而是当前默认预算。未来可依据多次大型项目数据改成“默认两次，
说明缺口并经用户批准后追加一次”，但不能恢复无理由的机械重试。

## D-03：为什么不增加监督 Subagent

常驻监督 Agent 需要读取主 Agent、Skill、writer 和 reviewer 的上下文，本身会造成新的
token 与顺序成本，也会产生“谁监督监督者”的问题。当前把可机械判断的监督下沉到
Hook：是否加载 Skill、Agent 顺序、命名空间、协议字段、调用次数和验收计数；把需要
判断的部分留给只读 reviewer。这样比再启动一个全程 Agent 更轻。

## D-04：Reviewer 为什么最多两轮

初审负责找遗漏，writer 修订后复审负责确认阻塞项已解决，已经构成完整闭环。真实试运行
出现 12 次 reviewer 启动，说明仅靠提示词会发生重复派发。第三次开始通常是在补充上下文
或重复确认，而不是产生新价值，所以运行状态记录 attempts 并拒绝第三次启动。第二轮仍
阻塞时应停下来报告，而不是继续消耗。

## D-05 与 D-06：为什么强制命名空间和机器协议

项目本地可能同时存在 `letsgo-reviewer` 和插件的 `lg:letsgo-reviewer`。不带命名空间会
启动到错误版本，还会让 token 报告把同一角色拆成两类。统一 `lg:` 既确定实现来源，也
便于观测；历史记录在报告时做别名归一。

同样，仅在 Agent 模板末尾规定 `LETGO_RESULT` 不够，因为主 Agent 的派发 prompt 曾明确
要求旧的 `LETGO_RESULT:` 格式。现在 Agent PreToolUse 会在启动前检查阶段、角色、状态和
必需字段。拒绝发生在运行前，比 Agent 完成后才发现结果不可解析更省成本。

## D-07：为什么 Apply 必须真实 TDD

TDD 门禁关注的是顺序和证据，不是文档里是否出现 RED/GREEN 字样。每个行为任务先运行
会因预期原因失败的最小测试，再做最小实现，最后整理并复跑。这样可以区分“测试真的
捕获了缺陷”和“实现后补了一个永远通过的测试”。

纯文档、注释、模板、仅测试和其他不改变生产行为的修改可以豁免，但必须写明理由、验证
命令和结果。豁免是可审查分支，不是随机跳过 TDD。

## D-08：为什么 Verify 必须零未验收项

自动测试只能证明它覆盖的行为。`stop-generation` 首次运行中，318 个测试全部通过，
reviewer 也通过，但浏览器验收 1–8 仍写着“待手动验证”。真实浏览器复验随后发现页面
白屏、reader 作用域错误和 Sidebar ref 错误。这个案例证明“测试全绿＋静态对照”不能
替代用户可见行为验收。

因此 verification 必须明确写 `未验证验收项：0`，且正文不能仍包含待手动/浏览器验证。
没有浏览器框架时应执行可复现的手动验收；环境确实不可用时保持 blocked，不能把待办
包装成通过。

## D-09 与 D-10：为什么使用两个单文件状态

`runtime-state.json` 只保存当前 session、变更和阶段的 Skill/Agent 门禁状态；阶段推进
后重置。`run-summary.json` 覆盖保存最近一次生命周期的阶段顺序和轻量指标。两者职责
不同，但都只保留一个文件，避免每次 Hook 调用生成大量 JSON。

指标中 `AskUserQuestion` 计入 `clarificationQuestions`，实际工具授权才计入
`permissionPrompts`；CodeGraph 调用、自动拒绝、Guard 拒绝和压缩也分别记录。分类的
目的不是追求一个漂亮数字，而是区分“需求本来需要用户决定”和“工具权限造成的摩擦”。

## D-11：为什么默认本地提交但不自动推送

生命周期到 done 后，代码、测试和证据如果仍留在工作区，交付并未真正形成可恢复版本。
本地提交可撤销、可审查，并且是生命周期的正常收尾，不应再创建 maintenance 变更。
但 push 会改变共享远端并影响其他人，所以仍需要用户明确授权。

提交只暂存当前变更的显式路径；如果工作区混有无法区分的用户改动，应停止而不是全部
暂存。提交后汇总必须来自 `git show --stat`，不能复用提交前的局部 diff 数字。

## D-12：为什么不直接放开所有 Node/Bash 命令

大量批准的根因常是 Agent 用 Bash 做本可由 Read/Glob/Grep 完成的读取，或者把多条命令
串起来。扩大 `node`/`bash` 白名单会让任意脚本获得写入与外部副作用能力。当前策略是：
模板要求优先原生只读工具、每次 Bash 只运行一条必要命令；守卫只自动放行可识别的测试、
语法检查和阶段内项目脚本，其余继续审查。目标是减少无意义批准，不是取消安全边界。

## D-13：为什么中文输出不会降低 Agent 效果

职责、方案、风险和证据使用简体中文，便于项目协作；代码、路径、命令、错误和 JSON 字段
保持原文。最后一行使用固定英文 ASCII 机器协议。效果主要由上下文质量和协议稳定性
决定，不由自然语言是中文还是英文决定；混合策略兼顾人读和机器解析。

## D-14：为什么恢复依赖文件状态

对话可能被压缩、终止或切换模型，不能假设主 Agent 永远记得已完成阶段。`status.json`
是生命周期事实来源，run summary 提供轻量顺序证据，`letsgo recover` 清理幽灵 runtime
并恢复唯一活跃变更。恢复后先读取状态，不重复已经完成的阶段。

## D-15：哪些规则应该成为硬门禁

硬门禁只处理能稳定、低成本判断的事实：阶段顺序、文件是否存在、TDD 证据结构、Agent
协议字段、次数上限和未验收项数量。方案质量、架构合理性和风险判断仍需要 writer、
reviewer 与用户。增加新门禁前应先有真实失败案例、明确的不变量和自动回归测试，避免把
个人偏好写成不可解释的限制。

## 维护规则

新增或修改关键设计时，至少记录：问题证据、选择、未选方案、代价、例外和重新评估条件。
如果规则进入 Hook 硬门禁，必须同时增加失败测试；如果只是建议，应明确它不会阻塞流程。
